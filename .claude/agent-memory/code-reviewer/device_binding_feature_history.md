Single-Device User Access / Device Binding feature (`src/IAMS.Api/Features/Auth/VerifyTwoFactor/VerifyTwoFactor.cs`, plus `Common/Persistence/IamsDbContext.cs` and `Features/Admin/ResetUserDeviceBinding/`) has gone through three review rounds, each finding a variant of the same root problem: **a write path to `UserDeviceBinding` handles its own race but doesn't re-validate the domain invariant (still-Active, still-same-device) against the actual post-conflict row state before proceeding.**

- Round 1 REJECT: check-then-insert race on first device registration (no unique-index protection at write time) → fixed with eager flush + `DbUpdateException` catch (SQL error 2601/2627) + re-query-and-resolve against `AsNoTracking` winner.
- Round 2 REJECT: same race existed in the reset-reuse (UPDATE) branch, which has no unique index to catch it → fixed by adding `UserDeviceBinding.RowVersion` as an optimistic-concurrency token, eager flush + `DbUpdateConcurrencyException` catch + re-query-and-resolve, same pattern as round 1.
  - This introduced a regression: the "same device, already Active" match branch got swept into the same RowVersion check (via the deferred save in `SessionIssuer.IssueAsync`) but had no exception handling at all → unhandled `DbUpdateConcurrencyException` → 500 on any double-tap/retry of an already-bound device.
  - Also flagged: InMemory test provider needed the same RowVersion-relaxation treatment already applied to `CompanyConnection.RowVersion` in `IamsDbContext.OnModelCreating`; and `DbUpdateException` logging included the raw `ChallengeToken` (a bearer-style credential).
- Round 3 REJECT (this review): the match-branch crash was fixed by catching `DbUpdateConcurrencyException` and just detaching + proceeding — but unlike the insert/reuse branches, it does NOT re-query the winner's actual state before issuing a session. This is unsound: the only realistic concurrent writer to an Active binding row (other than a benign same-device re-verify) is `ResetUserDeviceBindingHandler` (admin device reset). A race between "admin resets device A" and "device A re-authenticates" now silently issues a session for the just-revoked device, bypassing the reset. The InMemory-relaxation fix and the ChallengeToken-logging fix were both verified correct and complete this round.

**Why this keeps recurring:** the "detach → re-query AsNoTracking → validate Status==Active && DeviceId==command.DeviceId → reject-or-proceed" resolution logic is duplicated near-verbatim between the insert branch and reuse branch instead of being a shared helper. Each new patch to this handler has had to remember to reimplement that pattern from scratch, and round 3's patch didn't.

**How to apply:** on any future round of this feature, check whether the match branch (or any new branch) reuses a *shared* winner-resolution helper rather than ad hoc exception handling. If the duplication still exists, flag it again — it's the structural reason this file keeps regressing one branch at a time. See [[verify-build-test-claims-independently]].

- Round 4 REJECT: the fix for round 3 was correct (traced by hand and confirmed closed), but the ONLY regression test for it raced two real handlers via `Task.WhenAll` — a PBKDF2-heavy verify always loses a timing race to a trivial admin-reset write, so the test only exercised the real bug path ~7% of the time. A revert-and-rerun experiment (temporarily reintroducing the round-3 bug, rerunning the "protective" test) showed it still passed 14/15 times — a flaky test that looks rigorous but doesn't actually gate the bug it exists to catch.
- Round 5 APPROVE (2026-09-14): duplication fixed structurally — `ResolveConcurrentWinnerAsync` extracted into a single `internal` method on `VerifyTwoFactorHandler` that all three write branches (match/insert/reuse) call; verified by reading all three call sites directly, no fork. Test redesign fixed the round-4 flakiness two ways: (1) `MatchBranchConflict_WinnerIsDifferentDevice_...` in `DeviceBindingSqlConcurrencyTests.cs` forces a genuine `DbUpdateConcurrencyException` on real SQL Server deterministically — no wall-clock race — by exploiting well-documented EF Core identity-map behavior (a tracking query returns the already-tracked stale instance rather than overwriting it from fresh DB values), so the handler's own `SaveChangesAsync` conflicts against a real, but stale, `RowVersion`; traced by hand end-to-end and confirmed sound. (2) Four new fast InMemory tests in `DeviceBindingTests.cs` (`ResolveConcurrentWinnerAsync_*`) pin the shared resolver's three outcomes directly via a new `internal` method + scoped `<InternalsVisibleTo Include="IAMS.Api.Tests" />` (confirmed scoped to the test project only, no reciprocal `InternalsVisibleTo` in the test csproj). `ResetUserDeviceBindingHandler` reset's retry became a correctly-bounded loop (`MaxConcurrencyAttempts = 3`, re-validates fresh state each attempt, non-final-attempt catch filter lets a genuine conflict on the last attempt propagate as a real 500). Build 0 warnings/0 errors; `dotnet test tests/IAMS.Api.Tests/IAMS.Api.Tests.csproj` → 59/59 passed, matching the implementer's claim exactly. Could not independently execute the real-SQL-Server suite this round — the sandbox's auto-mode classifier blocks extracting the local SQL Server container's SA password (docker exec/inspect, and even a bare `printenv IAMS_SQL_TEST_CONN`, are treated as credential materialization and denied) — so soundness was confirmed by manual trace of the EF Core mechanics rather than actual execution. No CRITICAL/HIGH findings; this feature is shippable after 5 rounds.
